# EFG303 — Foreign-key validation and locking risk

## When it triggers

The migration adds a foreign key.

## Why it matters

Existing orphan rows can make validation fail, and validation can delay deployment while the database holds locks. For the supported providers, the repository's engine evidence records that validation can block concurrent writes until the transaction completes.

## Remediation

Validate and repair data before adding the constraint. Use provider-supported online or `NOT VALID` patterns where available, and measure lock duration against your own workload.

## Limitations

The locking claim is promoted to `HIGH`/`high` confidence only when the real SQL Server or PostgreSQL integration gate verifies it and the shipped provider engine evidence manifest covers EFG303 for that provider. Without engine evidence the finding is `UNVERIFIED`. EfGuard does not inspect existing rows or live workload.
